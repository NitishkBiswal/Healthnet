# Local demo patient and medical-record import flow

This workflow is for a local development/demo environment only. It creates four synthetic patient accounts, links their HealthNet identities, assigns two patients to each primary jurisdiction repository, and generates an import-ready CSV. It does not create real patient data.

## 1. Start infrastructure and apply migrations

From the repository root:

```powershell
docker compose -f infrastructure/docker-compose.yml up -d
```

Make sure the backend PostgreSQL schema is migrated before seeding. From `backend`:

```powershell
.venv\Scripts\Activate.ps1
python -m alembic upgrade head
```

Start the backend and frontend in their usual terminals. Confirm Keycloak is available at `http://localhost:8180` and that the HealthNet realm has loaded.

## 2. Seed demo patients

From the `backend` directory:

```powershell
python -m scripts.seed_demo_patients
```

The script is idempotent. It creates or reuses these Keycloak users, enforces the local demo password, assigns the PATIENT role, and creates or reuses the linked HealthNet identity:

| testpatient2 | Rohan Kulkarni | IN-KA | Karnataka |

The script resolves each jurisdiction against an ONLINE or DEGRADED repository in the HealthNet database. It stops with a clear error if either jurisdiction has no available matching repository. The Health ID is generated by HealthNet and printed by the script; it is not hard-coded.

The script generates `frontend/public/demo-medical-records.csv`. The Admin Portal's Medical Records Import tab exposes this file as **Download seeded demo patient records**.

## 3. Import through Admin

1. Sign in at `http://localhost:3000` as `testadmin`.
2. Open **Admin Portal → Medical Records Import**.
3. Download **Seeded demo patient records** (or use the file at `frontend/public/demo-medical-records.csv`).
4. Upload the CSV and choose **Import valid rows**.
5. Confirm the accepted count and that failed rows is zero.

The generated file includes four synthetic clinical rows per patient (Condition and Observation resources). The existing importer resolves every Health ID through the active Record Locator and writes the FHIR resources to that patient's assigned repository. It also records provenance and audit events. Conditions marked both chronic and emergency-relevant are added to the emergency summary.

## 4. Verify patient portal and consent

For each patient, sign in using its username and the local demo password above:

- `testpatient1` and `testpatient2` should show the Karnataka repository assignment.
- `testpatient3` and `testpatient4` should show the Odisha repository assignment.
- Open **Medical records** to confirm imported clinical data is visible.
- Open **Grant & revoke consents**, enter the doctor's HealthNet Provider ID, and grant `TREATMENT` / `clinical` consent.
- Sign in as the doctor and confirm the patient appears in the authorized-patient list and their records can be opened.

The doctor must be an active trusted provider. A patient grant is still required; seeding does not create consent on the patient's behalf.

## Safety and troubleshooting

- These credentials and synthetic records are strictly for local demos. Do not deploy them to production or use real patient information in this workflow.
- If the seeder reports no repository for `IN-KA` or `IN-OD`, inspect the repository registry's exact `jurisdiction` values and availability. Do not silently route a patient to a different jurisdiction.
- If the generated CSV link returns 404, run the seeder successfully and restart/reload the frontend dev server.
- If a FHIR import row fails, read the row-level error shown by Admin. The importer routes using the active Record Locator, not the patient's username.
- The demo seeder creates HealthNet identity and repository assignment records. The FHIR Patient resource is created by the first import for that Health ID, followed by the imported Condition and Observation resources.
